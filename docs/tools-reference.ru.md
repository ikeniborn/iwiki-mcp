# Инструменты

*Часть [документации iwiki-mcp](README.ru.md#документация). English version: [tools-reference.md](tools-reference.md).*

| Инструмент | Что делает |
|---|---|
| `wiki_search` | Режимы чтения — только `hybrid`, `lexical` и `semantic`; явный режим переопределяет `IWIKI_SEARCH_MODE` (по умолчанию `hybrid`), а публичный `vector` отклоняется. Summary-семантика страниц, lexical-совпадения страниц, graph-страницы, глобальные semantic-чанки и lexical-секции ранжируются независимо и объединяются RRF до финального top-k. Результаты содержат `hit` (`semantic`/`lexical`/`both`) и `source` (`seed`/`graph`/`global`/`lexical`). При заданном `IWIKI_RERANK_MODEL` точные актуальные чанки полного пула отправляются одним аутентифицированным LiteLLM batch с timeout 60 секунд, а provider `top_n` ограничивается запрошенным финальным `k`; сбой сохраняет предварительный порядок и возвращает только очищенные метаданные `rerank`. `scope`, `domains`, `k`, `threshold`, `type` и `tags` ограничивают read-поиск. `intent="write"` остаётся изолированным summary-vector поиском write-target и игнорирует read-режим/reranking; его target — bound primary, а первый названный домен используется только когда primary не привязан, и hosted-гейт авторизует тот же домен. На hosted-сервере каждый ответ дополнительно несёт `binding_source`, а ответ, чей scope пришёл из биндинга, а не из вызова — read без `domains` или любой write-intent lookup, — добавляет `binding_defaulted` в `warnings`. |
| `wiki_read_page` | Прочитать одну Markdown-страницу по домену и slug. С `heading` вернуть только одну секцию `##` (вместе с её `section_hash`) вместо всей страницы. |
| `wiki_list_pages` | Перечислить slug-и и файлы страниц в домене. |
| `wiki_related` | Вернуть связанные секции для id секции в пределах одного домена; форма `{"vector": [], "graph": []}` и domain-local fallback не меняются. |
| `wiki_write_page` | Проверить и записать новую страницу, проиндексировать домен и вернуть, удался ли авто-коммит базы. |
| `wiki_update_page` | Обновить существующую страницу: обновление только секции (`heading` + `new_body`), обновление только метаданных `code` или совмещённое атомарное обновление. С `new_heading` переименовать заголовок и атомарно переписать точные видимые входящие ссылки, если их домены доступны для записи. Принимает `expected_section_hash` для оптимистичной конкурентности. |
| `wiki_insert_section` | Вставить новую секцию `##` (позиция задаётся `after_heading` / `before_heading`) без переписывания остальной страницы. |
| `wiki_delete_section` | Удалить одну существующую секцию `##` без переписывания остальной страницы. Принимает `expected_section_hash`. |
| `wiki_move_section` | Переместить одну существующую секцию `##` (позиция задаётся `after_heading` / `before_heading`) без изменения её тела. Принимает `expected_section_hash`. |
| `wiki_delete_page` | Удалить страницу, записать delete-op, переиндексировать и синхронизировать базу. |
| `wiki_index` | Пересобрать индекс одного домена; по умолчанию использует привязанный домен write, если опущено. |
| `wiki_list_domains` | Перечислить видимые каталоги доменов в базе с размерами индексов. |
| `wiki_create_domain` | Создать пустой каталог домена и вернуть, удался ли авто-коммит базы; `index.jsonl` / `log.jsonl` домена создаются лениво в его корне при первой записи или переиндексации. |
| `wiki_bind` | Сузить PostgreSQL-область и в hosted HTTP-сессии опционально передать проектный объект `project_policy` (`specification_mode`, `max_snapshot_age_seconds`) для этой сессии — либо один `specification_mode` через устаревший одноимённый параметр, но никогда оба сразу; последующий вызов `wiki_bind` **заменяет** объект `project_policy` целиком, а не сливает его, поэтому bind, опустивший ранее заданное поле, возвращает это поле к hosted default; local PostgreSQL stdio отклоняет оба параметра, а для Git возвращается `project_config_manual_edit_required`, изменения выполняются вручную. |
| `wiki_status` | Показать разрешённую базу, каталог проекта, домены read, домен write и доступные домены. |
| `wiki_lint` | Read-only Markdown-authoritative отчёт: битые/reserved/unavailable-domain ссылки, сироты, stale-страницы, `missing_source` и пробелы секций, а также независимый per-domain SQLite graph parity (`state`, fingerprint, страницы, рёбра, anchors). Он не создаёт и не пересобирает кэш; non-ready или mismatch добавляет подсказку `wiki_index`. |
| `wiki_remediation_plan` | Сгруппировать текущие lint-находки в read-only план update/delete действий. |
| `wiki_migrate_okf` | Добавить OKF-фронтматтер и нормализовать type-каталоги автономно либо вернуть план для ревью. |
| `wiki_apply_okf` | Применить подтверждённые OKF-метаданные и решения по layout; при переносе страницы между type-каталогами атомарно переписать точные видимые входящие ссылки. |
| `wiki_export_okf` | Выполнить детерминированный in-place OKF sweep и пересоздать корневые `index.md` / `log.md`. |
| `wiki_sync` | Выполнить `git pull --rebase` и `git push` в базе. |
| `wiki_code_status` | Показать состояние build/read кодового графа, а также job текущего процесса, если `job_id` называет job из предыдущего `wiki_code_index`. См. [code-graph.ru.md](code-graph.ru.md). Без `job_id` возвращается текущий или последний build домена; id, никогда не выданный, устаревший или относящийся к другому домену, не ошибка — ответ содержит `job_unknown` в `warnings`. В PostgreSQL-хранилище локального build не существует, поэтому любой `job_id` заведомо неизвестен. |
| `wiki_code_index` | Построить или пересобрать локальный кодовый граф из checkout проекта, опубликовав его согласно `code_graph.publish_mode`, если он задан. См. [code-graph.ru.md](code-graph.ru.md). Отклоняется с `source_unavailable` на PostgreSQL-биндинге (нет локального checkout); `wait_seconds` ограничивает только время ожидания вызова, а не сам build, который продолжает выполняться до своего `max_full_rebuild_seconds`. |
| `wiki_code_search` | Искать типизированные сущности кодового графа (`kinds`: file/module/class/function/async_function/method) по `query`, префиксу `path` и `languages`. См. [code-graph.ru.md](code-graph.ru.md) и [code-graph-publishing.ru.md](code-graph-publishing.ru.md). В PostgreSQL-хранилище фильтр языков определяет активный опубликованный snapshot, а не конфигурация читающего сервера: язык, которого нет в snapshot, — `unsupported_language`, язык, который этот сервер не умеет парсить, — `invalid_config`. |
| `wiki_code_context` | Обойти кодовый граф в ширину от точных id сущностей (`seeds`, с префиксом `py:`/`ts:`/`js:`/`sh:` — брать их из `wiki_code_search`, никогда не qualified name), с ограничениями `depth`, `relations`, `max_nodes`, `max_files`, `max_source_bytes`. См. [code-graph.ru.md](code-graph.ru.md). При удалённом PostgreSQL-чтении `include_source=true` возвращает только структуру графа плюс `source_unavailable` вместо содержимого файлов. |
| `wiki_code_publish_begin` | Открыть одну владеемую сессию публикации для bound primary, при `code_graph.publish_mode = "mcp"`. См. [code-graph-publishing.ru.md](code-graph-publishing.ru.md). Требует hosted-сессию Streamable HTTP с аутентификацией, чей bound primary доступен для записи, иначе `unsupported_storage` / `unsupported_transport` / `unauthorized`; ответ сообщает действующие серверные `max_batch_rows` и `max_batch_bytes`, под которые нужно подгонять batch-и. |
| `wiki_code_publish_batch` | Принять один канонически сериализованный batch строк с совпадающим hash (`kind`, `ordinal`, `rows`, `payload_hash`) в открытой сессии. См. [code-graph-publishing.ru.md](code-graph-publishing.ru.md). Никогда не собирать batch вручную — пересобрать через `wiki_code_index` и передать публикацию `iwiki-mcp code publish`; повтор принятого `ordinal` с другими rows возвращает `batch_conflict`. |
| `wiki_code_publish_finalize` | Пересчитать ревизии и атомарно активировать один полностью застейдженный snapshot, заменив ранее активный snapshot домена. См. [code-graph-publishing.ru.md](code-graph-publishing.ru.md). |
| `wiki_code_publish_abort` | Отменить одну владеемую staging-сессию, не затрагивая активный snapshot. См. [code-graph-publishing.ru.md](code-graph-publishing.ru.md). Единственный способ выйти из наполовину опубликованной сессии. |
| `wiki_code_refresh_links` | Пересчитать Wiki-ссылки `DOCUMENTED_BY` одного домена относительно его активного опубликованного snapshot, не парся исходники заново и не резолвя символы. См. [code-graph-publishing.ru.md](code-graph-publishing.ru.md). Требует PostgreSQL-хранилище и hosted-сессию с аутентификацией и правом записи в указанный домен (домен передаётся явно, а не берётся из биндинга, поскольку устаревший биндинг сессии иначе перенаправил бы мутацию); без активного готового snapshot отвечает `missing_snapshot`, не запуская build. |
| `wiki_list_domain_grants` | Перечислить флаги read/write/manage-grants каждого токена на один домен, которым управляет вызывающий. Требует hosted PostgreSQL-сессию с аутентификацией (иначе `unsupported_transport`); администрирует доступ другого токена, а не собственную область вызывающего. |
| `wiki_set_domain_grant` | Выдать или изменить `can_read`/`can_write` другого токена на один управляемый домен (`can_write` требует `can_read`; grant, где оба флага `false`, отклоняется — используйте `wiki_revoke_domain_grant`). Требует hosted PostgreSQL-сессию с аутентификацией; никогда не использовать для расширения биндинга, отклонённого 403. |
| `wiki_revoke_domain_grant` | Отозвать grant другого токена на один управляемый домен. Требует hosted PostgreSQL-сессию с аутентификацией; `revoked: false` в результате значит, что у токена не было grant для удаления, а не ошибку. |
| `wiki_spec_search` | Искать спроецированные Given-When-Then сценарии по `query` в пределах `domains` (по умолчанию — bound read scope) с гибридным semantic/lexical ранжированием. См. [specifications.ru.md](specifications.ru.md). Только домены в режиме `disabled` исключаются из результатов; `mode` и `projection_state` каждого результата репортятся по домену, а пропуск `domains` отдаёт scope биндингу — читайте возвращённый список `domains`, прежде чем считать его проектным. |
| `wiki_spec_context` | Прочитать один сценарий вместе с сохранённым evidence резолюции и свежестью (`fresh`/`stale_spec`/`stale_graph`), не резолвя и не изменяя его. См. [specifications.ru.md](specifications.ru.md). Read-only; требует, чтобы домен был в read scope, а режим спецификаций не был `disabled`. |
| `wiki_spec_resolve` | Резолвить объявленные code-биндинги одного сценария относительно кодового графа и сохранить очищенный evidence (`resolved`/`ambiguous`/`unresolved`/`graph_unavailable`). См. [specifications.ru.md](specifications.ru.md). Требует write scope и никогда не расширяет биндинг или полномочия публикации кода; hosted — домен сценария должен быть bound primary, отказ называет, какое отношение биндинга не выполнилось (`invalid_domain`, `primary_not_selected`, `primary_not_writable`, `not_bound_primary`). |

`wiki_write_page` отказывается перезаписывать существующую страницу. У `wiki_update_page` три режима: обновление только секции требует пару `heading` и `new_body`; обновление только метаданных `code` принимает `code` и не меняет тело страницы — оно сохраняется байт в байт; совмещённое обновление атомарно выполняет оба действия. Опубликованная корневая JSON Schema остаётся простым объектом, где `domain` и `slug` остаются обязательными на верхнем уровне: валидация инструментов на стороне клиента отклоняет комбинатор в корне схемы, поэтому корневой `anyOf` привёл бы к тому, что клиент отбросил бы инструмент целиком. Взаимоисключающие режимы обеспечивает проверка во время выполнения, которая отклоняет частичные, пустые или небезопасные селекторы до мутации. Непустой корректный объект `code` полностью заменяет селекторы (`code.symbols`, `code.files`, `code.source_globs`); `{}` или объект со всеми пустыми списками очищает их; пропущенный либо `null` `code` сохраняет селекторы при обновлении секции. Ответ при обновлении только `code` опускает `heading` и не добавляет полей; ответы обновления секции и совмещённого обновления сохраняют `heading`.

```json
{"domain":"engineering","slug":"api/auth","code":{"symbols":[{"qualified_name":"auth.login"}],"files":[],"source_globs":[]}}
{"domain":"engineering","slug":"api/auth","heading":"API","new_body":"Updated login contract.","code":{"source_globs":["src/auth/**/*.py"]}}
```

Git сохраняет существующую проверку актуальности и строгую транзакцию спецификаций, затем один раз переиндексирует домен, создаёт коммит и обновляет граф. PostgreSQL использует текущий `expected_revision` как CAS в одной ревизии и одной транзакции; неизменённые чанки повторно используют embeddings. Повторная публикация делает Wiki-ссылки в Code Graph актуальными. `new_heading` необязателен при обновлении секции: он переписывает точные входящие относительные ссылки домена страницы и точные `iwiki://` ссылки видимых read-доменов. `wiki_apply_okf` использует ту же транзакцию только когда смена `type` переносит страницу. `wiki_insert_section` и `wiki_delete_section` добавляют или удаляют одну секцию `##`, а `wiki_move_section` переставляет одну секцию — все три без переписывания остальной страницы. `wiki_update_page`, `wiki_delete_section` и `wiki_move_section` принимают `expected_section_hash` (полученный из предыдущего `wiki_read_page(..., heading=...)`) для оптимистичной конкурентности: устаревший hash отклоняется с `section_conflict` вместо молчаливой перезаписи параллельной правки.

Междоменная операция начинается, только если каждый найденный видимый referrer входит в `write`; видимый read-only referrer блокирует её до изменения Markdown. Скрытые домены не инспектируются и не репортятся, поэтому никогда не переписываются. Результат дополняется полями `transaction_id`, `rewritten_pages`, `affected_domains` и `rewritten_links`.

Каждая междоменная операция держит блокировку mutation базы, stage-ит только затронутые Markdown и доменные `index.jsonl` / `log.jsonl` в корне, затем делает один локальный commit с `Iwiki-Transaction: <id>`. Её fsync-журнал находится в `.iwiki/transactions/<id>` и проходит `prepared` → `applied` → `committed` → `finalized`. Прерывание до commit восстанавливает snapshot; после commit — восстанавливает/помечает производный graph и финализирует журнал до следующей перекрывающейся мутации. Неоднозначное восстановление возвращает `manual_recovery_required`. Push остаётся fail-soft: локальный commit и переносимые authoritative-файлы остаются при ошибке публикации.

Разрешение project-relative stale-source остаётся отдельным audited follow-up; этот релиз не меняет его скрыто.

Сервер также предоставляет MCP-ресурс `iwiki://authoring-rules` с правилами структуры страниц.
